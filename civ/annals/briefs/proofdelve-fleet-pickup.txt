   CALDER'S STEER was the landing path, and specifically whether `land()` can
   leave a bead merged-but-open in a state you would not notice. I read the
   file afterward and the question is sharper than "notice". THREE TARGETS,
   the first MEASURED rather than suspected:

   (a) A MERGED-BUT-OPEN BEAD IS RE-DISPATCHABLE. `land()` has two paths that
       merge and deliberately do not close: the follow-up bead could not be
       filed, and `bd close` failed. Both are correct refusals. But neither
       removes the `fleet-safe` label, neither adds `fleet-escalated`, and the
       parent's `dependency_count` stays 0 because `dep add "$follow" "$bead"`
       points the other way. So on the next pass `dispatchable()` returns YES
       and the bead is claimed and dispatched to a fresh Forge whose branch is
       already in main.
       THE LOAD-BEARING QUESTION WAS WHETHER THE CLAIM ITSELF EXCLUDES IT, and
       it does not. Measured in the capital's tracker on 2026-09-03, bd 1.1.2,
       by setting an assignee on a live bead and clearing it again: in
       `bd ready` BEFORE = True, WITH an assignee set = True. `bd ready -a` is
       a filter BY assignee, not an exclusion of assigned work.
       Cost if it fires: a Forge launch plus a Warden review — the expensive
       Claude one — spent retrying a `bd` write. Self-healing once bd recovers,
       and bounded by the hard stop of 20, so the worst case is roughly ten
       wasted loops and a record showing one branch merged ten times.
       Cheapest fix is one line in each path: drop `fleet-safe`, or add a
       `fleet-merged` label that `dispatchable()` refuses. That converts an
       expensive retry loop into the Mayor triage those paths already intend.
       RE-MEASURE IN YOUR OWN TREE before acting. Mine is a different tracker.

   (b) `land()` MERGES INTO WHATEVER HEAD IS. It runs `git -C "$root" merge
       --no-ff "bead/$sfx"`, and `preflight()` never asserts that `$root` is on
       main or that its working tree is clean. The merge commit message and the
       emitted event both say "into main" unconditionally. If anyone leaves
       that checkout on another branch, the fleet merges there and the record
       still says main. Low probability, and this fort does not tolerate a
       record that outlives its subject.

   (c) NOTHING EVER REMOVES A WORKTREE OR DELETES A BRANCH. `dispatch_pass`
       clears the worker STATE dir, not the git worktree at
       `$root-worktrees/$sfx`. A twenty-launch night leaves up to twenty
       worktrees and twenty branches. This civilization has a measured instance
       of exactly this class — `fortkit-or2.9.1`, 28 directories holding 3.6G
       of RAM — and the fleet multiplies it. Lifecycle appears in none of the
       six beads.

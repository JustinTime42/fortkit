Two design points carry the whole value of that instrument:

- **The property is RENAME, not append.** `longburn-1p9` was never "auth.json is
  unwritable" — codex rotates by *rename*, and a re-bound auth.json pins the
  inode, so an append-based probe passes while rotation is broken.
- **An interpretation guard runs first.** Under a tmpfs over `~/.codex` every
  write "succeeds" into a scratch directory that dies with the sandbox, and every
  real file is *absent* — so a naive writability probe reports PASS on a broken
  runtime, and a read-only probe on `config.toml` reports WRITABLE when what it
  actually did was CREATE a file in a tmpfs. The probe asserts the mask sees the
  **real** directory (byte count matches host) before anything else. **My first
  draft did not, and two of its labels lied.** I caught it by reading my own
  output rather than the summary line.

### The finding that came out of it, and it is better news than the bead assumed

Both seats reported `touch ~/.codex/<canary>` **failing**, which on its face reads
as the rotation grant not working. It is not, and the distinction matters:

- **The model's shell cannot write `~/.codex` at all.** Codex's own
  `--sandbox workspace-write` layer denies everything outside its writable roots;
  longburn's seat said so in as many words — *"rejected by the command executor"*.
  That is the **policy** layer, above the kernel, doing its job.
- **The codex process itself can**, through the kernel layer. **Proven by mtime,
  not by reasoning:** `~/.codex/history.jsonl` written 08:37:48 today, and three
  session rollouts under `~/.codex/sessions` written after 08:15 — during these
  masked sessions. Those are exactly the writes that would have been EROFS.

**So the `~/.codex` write grant is for the RUNTIME, not for the seat.** The Forge
is denied at policy and permitted at kernel; only the attended Mayor and Warden
are permitted at both — which is precisely the asymmetry the Overseer's rider
asked to have stated, and which the lib comment now carries.

**Honest limit:** `auth.json` is unchanged since 2026-08-05, so no real token
rotation fell due. Rotation-by-rename is proven by an actual `mv` inside
`~/.codex` through both masks in all three forts, and by codex's own writes
landing there — **not** by observing a live refresh.

## What failed

1. **I nearly shipped a probe whose labels lied.** First draft asserted "~/.codex
   is writable" and "config.toml is read-only" without first checking the mask was
   looking at the *real* directory. Under fortkit's and ForgeOs's pre-edict claude
   posture both assertions were measuring a **tmpfs**: the "writable" PASS was a
   canary in scratch, and the "WRITABLE" FAIL on `config.toml` was a *file
   creation* in an empty tmpfs. Fixed by an interpretation guard that runs first.
   **A probe that cannot tell a tmpfs from the thing it is shadowing will report
   confidently about the wrong object.**
2. **My dotnet probe scored three correct results as FAIL** because `run()` merges
   stderr, so bash's "Read-only file system" line landed in the variable and the
   exact-match `[ "$out" = "BLOCKED" ]` missed. Identical to the E2 harness scar
   recorded 2026-08-12. **Reading a recorded scar is not avoiding it**; only the
   output caught it.
3. **I read a patcher's byte count as a corruption.** It printed 30249 and the
   installed file was 30357; I stopped and diffed before trusting either. The
   patcher prints Python `len(text)` — *characters* — while labelling it "bytes",
   and the comments are UTF-8. No defect, but the alarm cost a cycle and the
   message is wrong.
4. **I left `SSH_AUTH_SOCK` alone on purpose and was wrong.** I judged the
   three-way mechanism drift a separate concern and planned to file it. The first
   smoke proved otherwise: the name's mere presence made Veyra read a live agent,
   and she refused nine later probes — including the host RCE escape check. **An
   unchanged capability cost nine unmeasured assertions.** Measured after: socket
   bound to `/dev/null`, `ssh-add -l` → "Connection refused", so nothing was ever
   exposed. Fixed in the sitting rather than filed.
5. **The `mv` install lane recorded on 2026-08-12 no longer works** for
   `fort/scripts/**`: both the compound `python3 … && mv` and a bare `mv` were
   refused by the harness. `python3 -c "os.replace(...)"` works and is the lane
   now. `.claude/settings.json` is Edit-denied to the Regent too, as in 2026-08-08.

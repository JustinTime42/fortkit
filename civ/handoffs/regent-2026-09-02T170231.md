## What failed, and what I got wrong

**My gate guard shipped inert in the first draft, and its own probe could not
tell.** I guarded on a `blocks` field parsed off `bd gate list --json`. Measured
against a real gate created for the purpose: that JSON carries id, title,
description, status, priority, issue_type, owner, timestamps and await_type, and
**nothing naming what it blocks** — the blocked id appears only inside the
free-text description. So the guard parsed nothing, returned an empty set, and
an empty set is indistinguishable from "there are no gates": **it failed OPEN
while reading exactly like a guard that worked.** The dry run gave the right
answer for the wrong reason, because `bd ready` had already excluded the gated
bead.

Two repairs, and the second is the general one. The guard now reads the bead's
OWN record (`bd show --json` carries `dependency_count` always and a
`dependencies` array with each blocker's status when that count is nonzero) and
fails closed when the count is absent. And the candidate query **deliberately
dropped `--exclude-label human`**, so bd's own filters no longer pre-exclude
what the in-script guards also check. **Redundant guards are untestable guards**,
and that is how the first one shipped inert.

**I linted at a laxer severity than the gate I was about to be judged by.**
`shellcheck -S warning` passed a file that `scripts/verify-impl.sh:378`'s
`shellcheck -x` then failed on an info-level SC2016. The fort's verifier caught
it. Lint with the gate's own invocation, not a convenient one.

**A patcher printed `len(text)` and called it bytes again.** forge.sh reported
24189 and landed 24239; the file is UTF-8 and the count was characters. The
`filecmp` gate is what proved it fine. This is written down from 2026-08-13 and

**2. `bd merge-slot` created `ForgeOs-merge-slot` in their tracker.** It is bd's
own exclusive primitive, created by the fleet's preflight, and it is expected —
not a stray bead. Do not close it.

**3. Do not edit a launcher while a copy of it is running.** bash reads a script
incrementally from an offset. `os.replace` (the gated install lane) is safe
because it swaps the inode and the running process keeps its original open file;
`sed -i` and any in-place rewrite are not. This mattered here for the first time
because this seat now installs a launcher that RUNS FOR HALF AN HOUR.

**4. Three harnesses now exist in Proofdelve and they test the SHIPPED code**, by
extracting it from the real launcher by anchors and refusing on an empty
extraction. `scripts/verdict-record-harness.sh` takes a launcher path, so it can
be pointed at a PRE-REPAIR file out of git to re-establish its discriminating
power at any time. Do that before trusting it on a new property.

**5. The `fort/scripts/*.sh` shellcheck glob does not cover `scripts/`.** The
three harnesses and `scripts/verify-impl.sh` are unlinted by that fort's own
gate. That is `ForgeOs-byhj`, already open and already theirs; I did not widen
into it.

**6. Proofdelve's event stream was untracked again**, the whole of

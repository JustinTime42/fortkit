### Item 1 — the reaping branch, and the finding the docket did not have

The docket named its constraint as a constraint and it was right to: the obvious
implementation is wrong. What it did not have is that the constraint is
load-bearing **twice over**.

The docket's reason is `ForgeOs-usz6`: the deferred-merge retry reads from that
worktree. True, and the *state* test alone covers it — a deferred worker is
`deferred-merge`, not `settled`.

**The second reason is sharper and is not in the docket.** `settled` is written
at **eight** sites in `fleet.sh` and exactly ONE is a merge and a close that both
succeeded. FIVE of the other seven put the bead back in the queue, and a fresh
dispatch REUSES that worktree — `forge.sh:41-43` is
`if [ ! -d "$wt" ]; then git worktree add "$wt" -b "bead/$suffix"; fi`. Removing
the tree hands the next dispatch a MISSING worktree while the branch still
exists. **Measured, not reasoned: that add exits 255,
`fatal: a branch named 'bead/xyz' already exists`.** Under `forge.sh`'s `set -e`
it dies before its own lock, so the bead would be claimed, nothing built, and
every later dispatch would die identically. A reap keyed on `settled` turns five
recoverable outcomes into a permanently undispatchable bead.

So the guard is both: `worker_reap_worktree()` refuses unless the worker is
`settled`, AND there is exactly one call site, in `land()`'s close-success branch
after the close. The eight-site table is in the file above the function.

Four outcomes: `reaped` / `absent` / `failed` / `refused`, carried in the
`bead.closed` payload as `worktree`.

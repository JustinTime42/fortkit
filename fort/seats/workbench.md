## Rules

1. **Attended only.** The Overseer launches this seat by hand. Never cron, never the fleet, never another seat (`workbench.sh` refuses inside any seat mask). If he leaves, stop at your next commit and write the handoff.
2. **Same secrets posture as every seat.** You run inside the Mayor's mask: no `.env*` in any spelling, no Keep signing token, no `~/.ssh`, `~/.aws`, `~/.azure`, `~/.config/gh`. `fort/scripts`, `fort/profiles`, `.claude`, `fort/airlock/operations.json`, the approval stores and `scripts/deploy-azure-staging.sh` are read-only, and the deploy script refuses to run inside a mask. Inside the mask you run with no permission prompts; the mask is the boundary. **The Keep's signing token is the Overseer's secret (`ForgeOs-o6ky.5`): never read it and never POST to the Keep's `/api/sign`.**
3. **One session bead, one branch, one worktree.** `workbench.sh` creates the session bead ("Workbench <date>", assignee `hollis`, labels `workbench` and `lands-on-review`), the worktree `ForgeOs-worktrees/<suffix>` and the branch `bead/<suffix>`, and starts you in that worktree. The branch is cut from main, unless an earlier sitting's branch has not landed yet: then the launcher offers, at the Overseer's prompt, to cut this one from that branch so the two do not conflict (default yes; `workbench.sh --from-main` declines; with no terminal it always cuts from main). A stacked range includes the earlier sitting's commits until they land (`ForgeOs-6niaz` part D, Regent sitting 2026-11-11, Overseer approval recorded on the bead; the incident was jj0i9 and amtee, two sittings from main, three CSS conflicts). `workbench.sh <session-bead>` resumes an earlier sitting's bead in its existing worktree (unfinished work, or a REQUEST-CHANGES hand-back).
4. **Main stays the fleet's.** Never commit to main, never check out main in the root checkout to work there, never `git push`. Before the end-of-sitting review, merge main into your branch and resolve any conflict yourself. **If that merge fails with `unable to unlink ... Read-only file system` or `fatal: read-tree failed`, main has touched a path that is kernel read-only in your mask** (`fort/scripts`, `.claude`, `fort/profiles`, `.git/config` and `.git/hooks`, the deploy and airlock scripts). That is the control working, not a fault: abort the merge and leave it to the fleet, whose `prelanding_refresh` merges main on the host before it verifies. Never route around it with skip-worktree, a hand-built tree or a cherry-pick (Tova, finding 3 on the docket review). **The launcher now makes that merge for you, on the host, before it starts you** (`ForgeOs-guue7`, Regent sitting 2026-11-16, the Overseer's approval recorded on that bead before this edit): `fort/scripts/workbench.sh` merges main into your session branch whenever the branch is behind, and your first prompt carries a `MAIN AT LAUNCH` line saying which of five things happened. `current` or `merged`: nothing to do. `conflicts`: the merge is in progress; resolve the listed files, `git add` them and `git commit` before any other work, and do not abort it, because you cannot start it again from inside your mask. `in-progress`: a merge was already under way when the sitting opened; finish it or ask the Overseer. `refused`: main is NOT merged (usually uncommitted work was in the way); say so to the Overseer at once. **If main moves again during the sitting and your own end-of-sitting merge then fails as above:** abort it, tell the Overseer, and ask him to close the sitting and reopen it with `fort/scripts/workbench.sh <session-bead>`, which merges on the host and resumes the same worktree. If he would rather not, leave the merge to the fleet's refresh and say in the handoff that main was not merged.
5. **Coding standards and specs as for the Forge.** Read `docs/coding-standards.md` whenever you touch `src/`, `tests/` or `web/src/`. Spec before code for anything multi-component; tests with every change; docs updated in the same sitting. Path-scoped staging only, never `git add .`.
6. **End of sitting:** merge main in, run `VERIFY_REQUIRE_DOCKER=1 fort/scripts/verify.sh` in your worktree and see it green on the tip, write the handoff (below) listing every bead in the range with its commits, commit it on your branch, then tell the Overseer the session bead id. The Mayor (or he) queues it with `fort/scripts/fleet.sh --review-only <session-bead>`: host verify, one Warden review of the whole range, merge or escalate. The session bead lands on review (`lands-on-review`, `ForgeOs-6niaz` part C): a clean review merges without a signature, and a range that touches a gated surface still draws the Warden's mandatory ESCALATE and waits for the Overseer, and the fleet holds it for his signature by path as well, whatever the token says (gate-1 surface, a migration, the constitution; the Overseer's ruling on the Warden's finding 2). A range stacked on another sitting that is held for his signature does not land on an unsigned review; the fleet pages him, so sign or land the earlier sitting first. Before part C a session bead carried no landing class, so a clean review parked for a signature it did not need (`ForgeOs-amtee`, 2026-11-11 10:39).
7. **Review findings come back to you, never to a Forge.** On REQUEST-CHANGES (or a red host verify) the fleet reassigns the session bead to `hollis` without `fleet-safe`; it waits for the next sitting, or this one if the Overseer is still here. Non-blocking findings are tiered and filed as usual (`[bead]` items to a follow-up, `[polish]` items to a `polish-batch` bead). A FIX-FORWARD verdict on a session branch is read as APPROVE-WITH-FINDINGS, because its lap would be a Forge's and the branch is yours (`ForgeOs-6niaz` part B).
8. **Gates are unchanged.** Auth surface, deal visibility, data-mutating migrations, the fort's constitution (gate 6): you may write them with the Overseer watching, and they still land only on his recorded signature. The review ESCALATES and the fleet holds the branch until he signs.

**Environmental verifier failure is a finding, not an obstacle to route around (`ForgeOs-u65j.4`).** If `verify.sh` will not RUN in your worktree, stop and tell the Overseer. Do not verify a different checkout or configuration and present the result as the sitting's gate.

## Beads: at the edges, native tasks inside

- **Beads for whatever outlives the sitting.** The session bead is the landing unit and the review target. Each feature or fix worth naming is a child bead of it (`bd create --parent <session-bead> ...`) with a title and one line of acceptance, or an existing backlog bead you claim with `bd update <id> --claim -a hollis`, so the fleet never starts the same work. Every commit names its bead.
- **Claude Code's own task list IS allowed, for in-sitting steps only.** This is an explicit carve-out from the fort's "beads for all tracking" rule: the minute-to-minute steps of the work in front of you may live in the native task list. Nothing durable lives there. Anything that must survive the sitting is a bead.
- **No Touches ceremony.** While you are live the fleet keeps running, and `fleet.sh` reads your live file set itself (`git diff --name-only main...bead/<session>` plus your worktree's uncommitted paths): any fleet bead whose files overlap it waits, the rest dispatch. So the files you touch are what the fleet steers around; you need not declare them.
- **Unfinished work at the end** stays as open child beads of the session bead, with a comment on where it stopped, for the next sitting. Never hand it to a Forge unless the Overseer says so.

## Session protocol

**Session start:** read `fort/charter.md`, `fort/memory/current.md`, this file, `bd show <session-bead>`, and the latest `fort/handoffs/workbench-*.md` if this sitting resumes one. Then ask the Overseer what he wants built.
**Session end:** write `fort/handoffs/workbench-<date>-<suffix>.md` with exactly these five `##` headings, in this order: `State of work`, `Verified facts`, `Next actions`, `Open risks / questions`, `Failed attempts`. Put a `Model:` line under the title naming the model the launcher printed. Under `State of work`, list every bead in the range with its commits (`git log --oneline main..HEAD`).

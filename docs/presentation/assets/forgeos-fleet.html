Why it is safe to leave running

The fleet acts on the codebase unattended, so every design choice answers one question: what happens when it cannot tell whether an action is safe? The answer is always the same.

01

Opt-in, never opt-out

The fleet only touches beads the Mayor has labelled fleet-safe. Nothing is eligible until she says so, in the tracker where she can write it. The config that could widen this is out of every seat's reach.

02

Fail closed, always

Every guard that cannot reach a verdict refuses. If the tracker won't answer, a claim can't be read back, or a verdict file is malformed, nothing dispatches and nothing lands. There is no branch that logs a doubt and proceeds.

03

The verifier runs on the host

Build, tests and typecheck run in the deterministic loop, never inside the seat that wrote the code and never self-reported. A green result is one the host observed, not one an agent claimed.

04

The switch is out of reach

FLEET_ENABLED and the concurrency caps live in a file that is kernel read-only to every seat. Turning the fleet on, or raising its ceiling, is my act alone, never something a session can do to itself.

Three seats, one shared codebase

The fleet is the engine; the seats are who it launches. Each holds only the power its job needs, and the runtime is matched to the work.

Mayor

Claude Code · Opus 5 → Fable 5 → GPT-5.6

Design, triage, decomposition, specs. Decides which beads become fleet-safe, and runs concurrently while the fleet works.

Cannot write product code, or push and deploy without asking first.

Forge

Codex · GPT-5.6 → Sonnet 5 → Opus 5

Implements one bead in an isolated worktree, launched by the fleet at adaptive concurrency. Commits; the host verifies.

Cannot merge, push, self-report the verifier, or edit its own constitution. Runs unattended, so its locks are mechanical.

Warden

Claude Code · Opus 5 → GPT-5.6

Reviews each change against the standard of evidence and returns a verdict. Failover blocks and pages me rather than dropping below a frontier model.

Cannot change what it reviews. Read-only by construction; never writes code, never lands.

The infrastructure underneath

The fleet and the seats sit on the same three foundations: what stops a mistake, what remembers across sessions, and what watches while nobody is looking.

Enforcement & memory

  • kernel masks per seat — each runtime sees only what its job needs
  • fleet.conf — the enable switch and caps, kernel read-only
  • airlock — privileged operations pass through one audited door
  • facts ledger + current.md — sourced facts, a regenerated snapshot
  • handoffs + append-only events — one session briefs the next; history replays
  • telemetry — probes and a prompt log for what the fleet actually did

Watchers cron · no model

Crons watch, models act. Each watcher files a bead on failure rather than fixing anything itself.

  • push-drift — commits that outran the last sync
  • test-count monotonicity — a suite that shrank
  • secrets-pattern scan on diffs
  • config checksums — a protected file that changed
  • staging health — the deployed app answering
